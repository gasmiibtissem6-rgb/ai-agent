\addcontentsline{toc}{chapter}{Backend Implementation Contract}

\section*{Purpose}
This document is the implementation contract for \texttt{services/api}. It converts the product specification into backend work that can be reviewed, estimated, tested, and implemented module by module.

\section*{Backend Responsibility}
NestJS owns business logic, authorization, validation, state transitions, audit logging, signed URL issuance, and integration orchestration. Flutter and Next.js call API endpoints only. The Supabase service role key is API-only and must never be exposed to Flutter, Next.js, logs, or generated client bundles. Sensitive operations write audit records.

\section*{Authorization Rules}
JWT validation uses Supabase signing keys or verified Supabase auth middleware. The backend resolves a profile from the JWT subject before business methods run. Role checks use profile \texttt{is\_admin} and \texttt{admin\_role}. Deal access requires creator, linked party profile, matching invited email after acceptance, or authorized admin role. Service role access is available only inside server-side providers. Company permissions require active company membership and role checks.

\section*{Error Handling}
All responses use the OpenAPI success/error envelope. Required error codes are \texttt{VALIDATION\_ERROR}, \texttt{UNAUTHORIZED}, \texttt{FORBIDDEN}, \texttt{NOT\_FOUND}, \texttt{CONFLICT}, \texttt{VERSION\_CONFLICT}, \texttt{DEAL\_LOCKED}, \texttt{DUPLICATE\_PARTY}, \texttt{SUBSCRIPTION\_LIMIT}, \texttt{FILE\_TOO\_LARGE}, \texttt{PAYMENT\_CONFIGURATION\_MISSING}, \texttt{ADMIN\_ONLY}, and \texttt{INTERNAL\_ERROR}.

\section*{Testing Requirements}
Each module requires service unit tests, controller integration tests for authorization, validation tests for DTOs, and at least one negative permission test. Approval/version logic requires stale-version and locked-version tests. Admin and audit paths require append-only and permission tests.

\section*{Done Criteria}
A backend feature is done only when the endpoint exists, DTO validation exists, authorization exists, service logic exists, audit logging exists where required, tests exist, OpenAPI is updated, and the database schema supports the behavior.
