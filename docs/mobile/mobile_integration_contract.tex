\chapter*{Mobile Integration Contract}
\addcontentsline{toc}{chapter}{Mobile Integration Contract}

\section*{Purpose}
This document guides \texttt{apps/mobile} integration with the NestJS backend and the approved authentication/session model.

\section*{Current Status Correction}
Current branch evidence shows a Flutter foundation screen with IDEAL branding, main area cards, API configuration constants, endpoint constants, and simple backend readiness probes using Dart \texttt{HttpClient}. It does not yet show production auth screens, app routing, Riverpod auth state, Supabase initialization, password reset, deal screens, approval screens, file screens, or widget tests in the current branch. Those items are incomplete and must be implemented or refactored when introduced.

\section*{Architecture Rule}
Flutter owns UI and local state. NestJS owns business logic. Direct Supabase business logic in Flutter is temporary and should be removed. Flutter may use Supabase Auth only for session lifecycle if approved. No service role keys are allowed in Flutter.

\section*{API Client Requirements}
The base URL comes from \texttt{IDEAL\_API\_BASE\_URL}. The client attaches bearer tokens, parses the standard success envelope, parses the standard error envelope, handles timeouts, handles offline state, logs requests in debug only, and never stores service role keys.

\section*{Refactor Requirements}
Remove direct deal Supabase calls from Flutter, create a NestJS API client, keep Supabase Auth only if approved, move auth state into clean Riverpod providers when Riverpod is introduced, fix password reset redirects/deep links, add form validation, and add tests.

\section*{Done Criteria}
A mobile feature is done only when the screen exists, route exists, API client method exists, loading/empty/error/permission states exist, validation exists, errors are displayed, tests exist, and direct business Supabase calls are absent.
